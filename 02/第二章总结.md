### （1）socket和fd的关联？

在Linux系统里面，调用socket创建套接字后成功后，返回一个非负整数sockfd，后续的bind()/listen()/accept()/recv/send等等这些操作都是通过fd来引用内核中的socket对象。

具体的例子：

```c
创建TCP的套接字
int sockfd = socket(AF_INEF, SOCK_STREAM, 0); 
创建UDP套接字
int sockfd = socket(AF_INEF, SOCK_DGRAM, 0);
```

### （2）LT(level triggered)和ET(edge triggered)的区别？

        LT，只要读缓冲区里有数据没读完，epoll_wait就会一直返回这个fd，直到把数据都读走了。ET是只有当缓冲区从空变成非空时提醒一次。

<mark>举个例子</mark>，客户端给服务器发送30个字节，那么服务端recv每次接收10个字节，接收完30个需要3次，每次循环epoll_wait都会再次触发。

但是ET是接收了10个字节后epoll_wait就不触发了，剩下的20个字节会一直留在那里，直到客户端又发来新数据。



### （3）在epoll的情况下为什么需要封装reactor？

实现了网络IO和业务逻辑的解耦，具体来说

 1：epoll的recv数据的时候，直接读到一个buffer里面，也没有记录每个fd的epoll状态，也没有缓冲区管理，使得后续开发非常的杂乱。

        reactor封装了一个fd的结构体，把fd读写用到的内存，以及回调函数都写进去了，使得每个fd都有一个与之对应的内存和读写状态。

2：epoll把所有业务都写在了epoll_wait循环里面，网络和业务混在一起，每个业务都要重新开发。

        reactor有一个事件回调机制，会给不同的fd连接注册不同的回调函数，主循环中只判断什么状态来了调用什么回调函数，做什么由回调函数决定，把业务代码也封装进回调函数里，修改业务只要修改回调函数。

3：epoll中如果一次数据没接收完，下次还要重新分配，

        reactor中每个fd都有独立的内存空间。

       **因为epoll具有下面的几个痛点**，

1：作为事件管理框架，当有数据来的时候，它只会通知你这个fd可读了，但是数据要读多少，由谁来读，读完之后要干什么？这些操作epoll是没有的。

2：以及当新的EPOLLIN或者OUT事件来了，该做什么都写在mainloop里面，也就是说状态管理太散乱了，到后面会形成一个面条式的代码。

        **Reactor为了解决epoll的这些问题**，

1：解耦网络开发和业务开发：在EPOLL的基础上封装了一个回调机制。Reactor把发生了什么事情变成了调用哪个回调函数，你只需要注册一个read_cb和write_cb，reactor收到事件之后自动回调，上层开发完全不用知道epoll的存在，只需要关注回调函数内部的逻辑即可。

2：reactor还解决了粘包的问题：会给reactor封装rbuffer，使得LT触发的来的数据能先放进缓冲区，等拼接成一个完整的数据包后再触发业务回调处理。

举个例子，在实现webserver和websocket之后，reactor使得网络层只要在epoll_wait中关注事件，然后有事件来了调用对应的回调函数。而业务部分只要实现接口函数就行了。



<mark>举个例子</mark>，比如说现在conn结构体的rbuffer_len只有1024，但是我淘宝发过来的http请求很多，超过1024怎么办？

把rbuffer做成一个链表，网络层接收到数据后，分配1024的块然后入队，下次再要再分配。

## （1）listen(sockfd, backlog)中的backlog是什么？怎么设置？

backlog参数随着Linux的迭代，最开始的作用是表示半连接队列sys-que，然后表示syn_que和accept_que的总长度，最后是表示accept_que队列的长度。

该参数虽然是表示等待监听的队列长度，但实际的队列长度受到内核参数somaxconn的影响，对于高并发场景这两个参数都要调整。

## （2）close和shutdown的区别？在一个多线程程序中，如果两个线程同时持有一个socket的fd，其中一个线程调用了 `close`，另一个线程还在 `recv`，会发生什么？双方同时调用close会发生什么？

1 close(fd)指的是释放文件描述符，双向都关闭。而shutdown只有断开本端的连接，实际开发中不建议使用shutdown。

2 取决于socket是否被完全释放，如果处于释放中，那么还会recv。如果完全释放了，recv立即放回0。

3 双方同时调用close，从状态图中可以看出，双端会同时经过wait1, closing, time_wait, closed



## （3）大量出现TIME_WAIT与 CLOSE_WAIT的原因？解决方案？

        time_wait是发送方在发最后一个ack后进入的状态，服务端出现大量等待，说明服务端在主动关闭连接

        close_wait是被动关闭方没有调用close导致的。此时tcp处于半连接，本段要调用close释放fd



## （4）三次握手完成后，客户端已经可以 `send` 数据了，但此时服务端的 `accept` 函数还没返回，这种情况下数据会去哪里？是直接丢弃还是被内核缓存？

        这种情况下数据会被缓存在服务端的Linux内核里，等待accept了一个fd之后，从内核中recv取出数据。如果这时候数据太多，缓冲区满了，那么服务端会将接收窗口设置为0，通知客户端停止发送。这就是TCP的流量控制。



## （5）如果攻击者只发送 SYN 包，不发送第三次 ACK，服务端会怎样？如果此时 `backlog` 队列满了，合法的客户端会受影响吗？

        只发送syn，那么服务端多次接收了syn就会多次发送syn+ack，如果半连接队列syn_que满了，那么会影响新客户端的握手。如果accept_que满了，则会影响已经established客户端发送数据。



## （6）三次握手发送在哪些函数里？第三握手数据包，如何从半连接队列查找匹配的节点？

        三次握手从客户端的connect函数开始，第二次握手在服务端的listen之后，且在内核中完成。第三次握手完成，是在客户端的connect函数返回之前，服务端完成是在accept函数完成之前。服务端从全连接队列取出已完成的连接，`accept()`返回。

        从半连接队列查找匹配的节点是通过四元组来查询。TCP头有sport，dprot。IP协议里有sip，dip。内核将`request_sock`从半连接队列移除，创建一个完整的`struct sock`（表示已建立的连接），放入全连接队列（Accept Queue），等待`accept()`取走。



## （7）UDP和P2P的区别？TCP和UDP的区别？

        UDP是传输协议而P2P是传输架构，P2P可以用UDP来实现。

       TCP和UDP二者的区别

            1: TCP是基于连接的，而UDP是基于数据包的。TCP上客户端和服务端都会有一个连接，是一对一的，也是顺序的，先发来的包先收到。而UDP是没有顺序的，会有分包和粘包的问题。

            2：对于TCP分包和粘包的问题，可以在应用层对数据进行封装，比如说用头两个字节来表示数据包长度，接收的时候先解析这个长度头，再判断数据长度和头长度是否一致。或者在数据中加入分隔符，从而分割不同的数据包。而UDP是需要为每个数据包分配id值。

            3：并发做法不同，TCP只要通过epoll的方式就可以实现，而UDP需要模拟TCP的方式来建立连接。

            4：使用场景不同，UDP适用于实时性强的，适合需要低延迟的场景，还有一个就是数据下载的时候，两者是或的关系。而TCP不用考虑这么多

            5：UDP是偏向于短链接（发起一次请求，不用建立连接，只要发包和收包就行了），而TCP偏向于长连接。

## （8）TCP如何实现可靠传输的？

        滑动窗口：**用于实现流量控制**，确保发送方的速率不超过接收方的处理能力。接收方在每次回复的ack包中会带上自己的窗口大小，发送方根据这个窗口来判断字节已发送但还未确认的数据总量

        延迟确认：接收方收到数据后不会立即发送ack，而是会在一个延时内收到多个包后合并成一个ack发送

        拥塞控制：为了防止网络过载，**拥塞窗口（cwnd）**。它由发送方根据网络反馈动态维护。发送方最终能发送的数据量是`min(接收方通告窗口rwnd, 拥塞窗口cwnd)`。

         慢启动：刚开始建立连接时，发送少量数据包，随着ack的接收，发送的数据包数量指数增长，然后到达阈值后再线性增长。通过指数级增长去快速占满网络容量，当遇到丢包或达到阈值后，才转为更保守的线性增长。这体现了TCP‘**慢启动，快收敛**’的设计哲学。

## （9）三次握手和四次挥手分别解决什么问题？

三次握手：**解决了“通信双方在建立连接前，确认彼此的收发能力正常”的问题。**

        1：同步序列号；2：确保双方收发能力；

四次挥手：**解决了“全双工连接的双向独立关闭”问题**。

        TCP是全双工的，意味着**数据收发是两个独立的方向**。四次挥手的核心就是让两个方向可以**分别关闭**。

面试题

## （1）为什么要有协程?它解决了哪些痛点？

        协程是同步的编程方式，异步的性能。解决了在传统epoll+非阻塞io情况下，每个epoll状态有对应的业务回调，但是当业务比较复杂，需要嵌套回调函数的时候，业务就会被拆分开。

        1：业务逻辑被拆分：

      <mark>  举个例子</mark>服务器接收到客户端请求，要查数据库，调用第三方API，然后返回response。在recv接收到request之后，调用db请求的回调函数，db查完后又调用http请求的回调，然后又调用send发送response。

        但是如果是协程的话，只要把代码上述所有这写代码顺序进一个句柄函数即可，这个函数里的recv在等待时会挂起，不阻塞线程，然后调度器会把当前协程的上下文保存到内存，并切换协程状态注册到epoll里等待fd可读。然后调度器从就绪队列中取出下一个可以运行的协程并resume恢复这个协程。这样会使得代码是纵向的顺序的，和同步的写法一样。

        2：系统开销不一样。虽然都是异步的处理框架，线程切换是在内核空间，创建开销也很高。而协程切换在用户态，创建开销很低，而且响应更快。

        3：相比于epoll的事件通知，业务要维护很多复杂的状态。而协程只要把状态（上下文）保存进寄存器即可，用框架来管理。



## （2）进程/线程和协程有什么区别？为什么有了线程还要协程？

### 进程、线程与协程的区别

**进程**是系统资源分配的最小单位，拥有独立的内存空间，进程间切换开销最大，需内核参与，稳定性最好，一个进程崩溃通常不影响其他进程。

**线程**是CPU调度的最小单位，属于同一个进程的多个线程共享进程的内存空间，切换开销中等，由内核调度。

**协程**是用户态的轻量级执行流，完全由用户态调度器（如`epoll`+调度器）管理，切换无需内核参与，开销极低（纳秒级）。它本质是在线程之上运行的多个子任务。

### 为什么有了线程还要协程？

核心原因是**线程太重，而协程更轻、开发体验更好**。

1. **创建与切换开销**：线程创建占用固定栈（如8MB），切换需要陷入内核态，微秒级开销。协程初始栈（如2KB）极小，切换在用户态，纳秒级，支持百万级并发。

2. **解决回调地狱**：`epoll` + 非阻塞IO虽性能高，但用回调处理复杂业务逻辑时，代码被拆散到多个回调中，可读性差、状态维护难。协程允许用同步顺序的写法实现异步性能。

```c
void handle_request() {
    char buf[1024];
    recv(client_fd, buf, ...);          // 协程挂起等待，不阻塞线程
    char *result = db_query(buf);       // 同步写法，自动让出
    char *response = http_request(result);
    send(client_fd, response);
}
```



## （3）协程实现方法有哪些（三种）？有什么优缺点？代码实现过程是什么样的？

        协程的实现有三种方法：setjmp/longjmp，ucontext，汇编实现

        协程的实现本质：事件没有就绪则切换，事件如果就绪了就恢复。把等待的时间拿去做其他事情。



        1 setjmp、longjmp：

            int setjmp(jmp_buf env);把执行这个函数的上下文信息保存进env里，初次调用返回值是0；

            void longjmp(jmp_buf env, int val);跳转到env中保存的上下文中，去执行setjmp，且并且返回值是longjmp的第二个参数val。

        这两个函数中的上下文信息，其实就是程序在对应位置时的寄存器取值，常见的寄存器有程序计数器PC，用来保存程序对应的下一条指令的位置。

        2 ucontext：

            是标准的POSIX接口，主要有getcontext(), setcontext(), makecontext()以及swapcontext组成，上下文的定义主要由ucontext_t结构体组成，当协程挂起，调度器会切换到uc_link对应的上下文完成切换。还有uc_stack为上下文中使用的栈（控制协程数量）以及uc_sigmask为上下文中的阻塞信号集合，以及寄存器的值。

            **getcontext获取当前上下文，setcontext设置当前上下文，swapcontext切换上下文，makecontext创建一个新的上下文**。

        3 汇编实现：

        保存现场用的RDI，恢复用的是RSI。

        （1）协程切换函数：保存当前协程的寄存器现场到 [RDI]；保存栈顶指针RSP；保存当前指令指针 RIP；

                                            恢复目标协程的寄存器现场从 [RSI]；恢复栈顶指针；恢复指令指针：jmp跳转到保存的 RIP

        （2）入口函数：

                    RDI = 协程上下文指针；RSI = 入口函数指针；RDX = 栈空间起始地址；RCX = 栈空间大小；设置入口函数为 RIP；设置栈顶指针：从栈底开始（栈向下增长）；把入口函数地址压栈，这样第一次切换时，ret指令会直接跳转到入口函数

setjmp/longjmp标准C就有的接口，跨平台性最好；ucontext很方便使用，但是不同的平台用法会不一样；汇编的适配受到CPU平台的限制。性能最好的是汇编，其次是setjmp，ucontext第三，但是性能不会相差太大。



## （4）协程切换时，具体需要保存和恢复哪些寄存器？

**协程切换时，必须保存和恢复所有“被调用者保存（Callee-saved）”的寄存器，以及栈指针 `RSP` 和指令指针 `RIP`。**

在 x86-64 架构下，寄存器分为两类：

| 类型                          | 寄存器                                           | 谁负责保存               | 协程切换时需不需要保存？                              |
| --------------------------- | --------------------------------------------- | ------------------- | ----------------------------------------- |
| **调用者保存寄存器（Caller-saved）**  | `RAX`, `RCX`, `RDX`, `RSI`, `RDI`, `R8`-`R11` | 调用者（caller）在函数调用前保存 | **不需要**，因为编译器已经生成了保存和恢复它们的代码，它们不会跨越函数调用边界 |
| **被调用者保存寄存器（Callee-saved）** | `RBX`, `RBP`, `R12`-`R15`                     | 被调用者（callee）负责恢复    | **必须保存**，调用者期望这些寄存器在函数返回后保持不变             |
| **特殊寄存器**                   | `RSP` (栈指针), `RIP` (指令指针)                     | N/A                 | **必须保存**，是切换执行流的根本                        |

* * *

协程切换时必须保存的寄存器清单

```c
struct co_context { // 被调用者保存寄存器（Callee-saved） 
void *rbx; 
void *rbp; 
void *r12; 
void *r13; 
void *r14; 
void *r15; 
// 栈指针和指令指针（核心） 
void *rsp;
void *rip;
};
```

* * *

为什么是这些寄存器？

| 寄存器             | 作用                        | 不保存会怎样？              |
| --------------- | ------------------------- | -------------------- |
| **`RSP`**       | 栈顶指针，决定了协程的栈空间位置          | 恢复时无法找到正确的栈，局部变量全部错乱 |
| **`RIP`**       | 指令指针，决定下一条执行的代码           | 恢复后无法从挂起点继续执行        |
| **`RBP`**       | 栈帧基址，用于定位局部变量和参数          | 函数调用链断裂，局部变量访问错误     |
| **`RBX`**       | 通用数据寄存器，常被编译器用来保存跨函数调用的数据 | 数据丢失，计算结果错误          |
| **`R12`-`R15`** | 通用寄存器，ABI 规定需被调用者保存       | 同上，数据丢失              |



## （5）协程如何定义（struct coroutine）？调度器如何定义（struct scheduler）？调度器的执行策略？

用协程解决网络IO处理的开源框架。10w个协程，如何组织到一起。

1 协程运行体定义：

```c
typedef struct _nty_coroutine {
    nty_cpu_ctx ctx; // 保存的上下文

    // 运行体本身
    proc_coroutine func; // 协程的子过程回调函数
    void *arg; // 回调函数参数
    void *stack; // 协程独立的栈空间
    size_t stack_size; // 栈大小

    // 状态管理
    nty_coroutine_status status; // 状态：就绪/睡眠/等待
    uint64_t birth; // 创建
    uint64_t id; //

    // 调度器指针
    nty_schedule *sched;

    // 多个状态集合的挂载点
    RB_ENTRY(_nty_coroutine) sleep_node;// 红黑树节点，挂载到睡眠树
    RB_ENTRY(_nty_coroutine) wait_node;// 红黑树节点，挂载到等待树
    TAILQ_ENTRY(_nty_coroutine) ready_next;// 队列节点，挂载到就绪队列
    TAILQ_ENTRY(_nty_coroutine) defer_next; // 延迟队列节点

    // io相关
    int fd;    // 关联的sockfd
    int events; // 关注的epoll事件（EPOLLIN/EPOLLOUT）
} nty_coroutine;
```

关键设计点，协程同时只属于一个状态，但会在ready/sleep/wait三种状态中迁移。

2 调度器定义：

调度器是管理所有协程的全局单例，负责协程创建，调度，状态迁移和IO事件轮询

```c
typedef struct _nty_schedule {
    // 1. 三个状态集合（核心！）
    TAILQ_HEAD(, _nty_coroutine) ready;      // 就绪队列（无优先级，FIFO）
    RB_HEAD(sleep_tree, _nty_coroutine) sleep; // 睡眠红黑树（按超时时间排序）
    RB_HEAD(wait_tree, _nty_coroutine) wait;   // 等待红黑树（等待IO就绪）

    // 2. epoll相关（IO事件管理）
    int epfd;                 // epoll文件描述符
    struct epoll_event *events; // epoll_wait返回的事件数组
    // 3. 当前运行态
    nty_coroutine *curr_thread; // 当前正在运行的协程
    nty_cpu_ctx ctx;           // 调度器自己的寄存器上下文（用于从协程yield回来）

    // 4. 配置参数
    size_t stack_size;        // 每个协程的默认栈大小（所有协程一致）
    uint64_t spawned_coroutines; // 已创建的协程总数（用于生成ID）
    
    // 5. 线程局部存储（TLS）
    // 调度器实例存储在线程的私有空间中（pthread_setspecific）
    // 保证每个线程有独立的调度器
} nty_schedule;
```

* **三个状态集合使用不同数据结构**：就绪用**队列**（因为无优先级，FIFO即可）；睡眠和等待用**红黑树**（需要按超时时间或fd排序，快速查找最小超时或特定fd）。

* **调度器本身也保存上下文**（`ctx`），这是实现 `yield` 到调度器、再从调度器 `resume` 其他协程的关键。



 策略一：生产者-消费者模式（文章7.1）

* 核心逻辑：一个线程负责生产（`epoll_wait` 检测到IO事件），另一个线程负责消费（执行协程回调）。

* 缺点：引入了线程间同步（锁、条件变量），增加了复杂性，且有上下文切换开销。

策略二：多状态运行（文章7.2，NtyCo实际采用）

* 核心逻辑：**一个线程内完成所有工作**。调度器的主循环（`nty_schedule_run`）不断循环，依次处理：
  
  1. **检查睡眠树**：将超时的协程移入就绪队列。
  
  2. **检查等待树**：调用 `epoll_wait`，将IO就绪的协程移入就绪队列。
  
  3. **从就绪队列取出一个协程**，调用 `resume` 恢复执行。
  
  4. 协程运行中若遇到IO阻塞，调用 `yield` 回到调度器，调度器继续循环。

## （6）协程本体，以及调度器如何使用？举一个例子？

        比如说现在要实现一个echo服务器，客户端有连接过来了，服务器接收数据并send回去。使用ntyco实现，代码风格和同步阻塞写法基本一样。

1：创建协程调度器并启动服务

        在main里调用nty_socket（设置为非阻塞io）创建监听fd，并listen。然后nty_coroutine_create创建一个协程，并把accept_loop回调函数和参数fd，以及协程对象都放进去，把新的协程加入就绪队列了。

        接着nty_schedule_run()启动调度器，此时调度器开始循环调度。

2：主协程-不停接收新连接

        在accept_loop函数中接收传入的sockfd，并循环接收新连接，循环内部调用nty_accept，返回clientfd。如果clientfd==-1表示没有新连接，则yield挂起并切换。如果有连接，则创建一个子协程，调用client_handler的函数，处理这个客户端。

        这一步是由调度器从就绪队列中取出accept_loop，resume执行的，然后在loop内部的nty_accept中，会把这个fd加入epoll事件循环中，来监听EPOLLIN。然后把协程移入wait_tree，最后yield切换回maincontext。直到调度器监听到协程accept_loop就绪了，那么resume恢复并得到clientfd，然后再创建客户端处理的协程如recv等，并由调度器加入就绪队列中。

3：在client_handler函数中，也有while循环recv接收数据，写法也和同步类似的，但是nty_recv的实现底层就是异步了：首先要获取当前允许的协程，然后先尝试recv，如果数据就绪那么直接返回。如果没有就绪，就把fd加入epoll事件中，并把协程状态修改为wait，并移入等待树。接着yield让出CPU。一旦检测到fd，则调度器会resume会这个协程，那么执行recv接收数据。



调度器是有一个nty_schedule_run无限循环的，不断resume就绪的协程。



## （7）协程调度器的核心数据结构有哪些？为什么？

1 ready就绪 用队列

        因为所有协程优先级一致，不用优先级排序。先就绪的先执行。入队（创建/唤醒）和出队（调度执行）是高频操作。并且是O(1)复杂度，效率最高。

**使用场景：**

* 新创建的协程 → 插入队尾

* epoll_wait返回IO就绪的协程 → 插入队尾

* 睡眠超时的协程 → 插入队尾

* 调度器每次从队头取一个协程执行



2 sleep睡眠 用红黑树

        因为要按时间排序，快速找到最早超时的协程。协程可能随时sleep，也可能被提前唤醒。插入O(log n)，查找O(log n)，删除O(log n)，每次循环需要找出所有 `超时时间 < 当前时间` 的协程，需要一个强查找的算法。

**红黑树存储形式：**

* Key：超时时间戳（`birth + sleep_duration`）

* Value：协程指针

触发场景：业务逻辑要延迟执行，比如限流或者重试间隔，或者是定时器5s上报一次状态。





3 wait等待 也用红黑树

        epoll_wait返回fd后，需要快速找到对应协程。等待IO也有超时，需要和睡眠树类似的时间排序。fd就绪时，需要从等待树中删除，O(log n)

        等待（wait）集合，其功能是在等待IO准备就绪，等待IO也是有时长的，所以等待（wait）集合采用红黑树的来存储

触发场景：

* `nty_recv` 时，socket缓冲区无数据（`EAGAIN`）

* `nty_send` 时，socket发送缓冲区满（`EAGAIN`）
* `nty_accept` 时，无新连接



"调度器有三个核心集合：**就绪队列用TAILQ**，因为所有协程优先级相同，FIFO调度，入队出队都是O(1)，效率最高。**睡眠树和等待树都用红黑树**，睡眠树需要按超时时间排序，每次快速找出所有超时的协程；等待树需要按fd查找，同时也要支持超时检查。红黑树插入、删除、查找都是O(log n)，最坏情况有保障，比哈希表更稳定，比堆更灵活（支持任意删除）。epoll是调度器的核心组件，负责管理所有协程的IO事件，通过data.ptr直接指向协程，实现事件到协程的快速分发。这套设计借鉴了nginx和Linux内核的思想，在性能和功能之间取得了很好的平衡。"

## （8）协程遇到IO阻塞怎么办？（Hook机制，高频重点！）

        代码里可以通过fcntl(fd, F_GETFL, 0)来设置非阻塞fd，

> ⚠️ **重要**：非阻塞 ≠ 异步。非阻塞模式下，应用程序仍需**主动轮询**或**事件通知机制**来知道数据何时就绪。

如果是在ET触发时，设置在非阻塞状态下，则进入fd可读EPOLLIN状态，recv数据时，需要在n<0状态判断是否有Eagain标志，如果有表示读完了，没有则表示还要一直循环读取。

LT触发就不用非阻塞了，因为如果有数据没读完，LT触发会一直触发epollwait循环读取数据。



协程遇到阻塞IO，通过hook+调度器，把阻塞变成非阻塞但同步的写法。

<mark>举个例子：</mark>把原先的系统调用如read和write改为协程友好的非阻塞版本。第一步是要用dlsym来获取read和write的真正地址，并保存进read_f函数指针内。第二步是要定义自己的read函数，函数中int res = poll(fds, 1, 0);  // timeout = 0，立即返回，然后检测res如果<0，那么挂起，调用swapcontext（）切换上下文，如果数据被读到了就绪了，则调用read_f真正去读取数据。在编译的时候会优先使用我们定义的read，而真正的系统read指向read_f地址。



**“Hook 的实现主要依赖动态链接器的符号查找机制。我们通过 `dlsym(RTLD_NEXT, "read")` 获取 libc 中真正的 `read` 函数地址，然后定义一个同名的 `read` 函数来替换它。在自定义的 `read` 中，我们先用 `poll` 非阻塞地检测 fd 状态，如果就绪则直接read_f读数据；如果数据未就绪，调用epoll_ctl(epfd, epoll_ctl_addm fd, &env)把 fd 加入 epoll 等待，并通过 `swapcontext` 挂起当前协程（yeild），然后切换会maincontext；调度器统一判断fd状态，如果这个fd可读了，则由调度器恢复协程。这样，上层业务代码看起来调用的还是标准的 `read`，但底层已经是非阻塞的协程调度了。”**
