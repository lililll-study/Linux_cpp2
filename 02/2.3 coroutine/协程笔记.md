#### a. 实现背景

    epoll + io非阻塞模式下（异步回调）

```c
while (1) {
    int nready = epoll_wait(epfd, events, 1024, -1);
    for (i=0; i<nready; i++) {
        if (events[i].events & EPOLLIN) {
```

这种情况下，代码被撕碎了，一个完整的业务逻辑被拆分成多个回调函数，难以维护。



    例如需要完成一个：接收客户端请求 —> 查数据库 —> 调用第三方API —> 返回response的过程

用epoll实现如下：问题是，业务逻辑被拆分了，很复杂

```c
void recv_cb(int fd) {
    recv(fd, request, ...);
    // 发起查询请求
    db_query_async(request, db_cb); // 跳转第二步
}

void db_cb(result) {

    // 处理 DB 结果...
    // 发起 HTTP 请求（非阻塞）
    http_request_async(url, http_cb);  // ← 跳到步骤3
}


// 步骤3：HTTP 请求完成
void http_cb(response) {
    // 处理 HTTP 结果...
    send(fd, response, ...);  // 返回
}
```



因此协程需要实现的是：<mark>用同步的编程方式，实现异步的性能。</mark>

实现方法如下：

```c
void handle_client(int fd) {
    char request[1024];
    recv(fd, request, 1024);           // ← 看起来是阻塞的，实际上会“让出”CPU

    char *db_result = db_query(request); // ← 看起来是同步的，实际会“让出”CPU

    char *http_result = http_request(db_result); // ← 看起来是同步的，实际会“让出”CPU

    send(fd, http_result, len);        // ← 返回
}
```

### （2）协程原语（本质就是下面三个函数）

| 原语         | 作用                                                  | 类比              |
| ---------- | --------------------------------------------------- | --------------- |
| **create** | 创建一个协程，分配栈空间，初始化上下文                                 | 招一个临时工          |
| **resume** | 启动或恢复一个协程的执行。从mian函数中恢复一个协程的过程。                     | 喊一声“继续干活！”      |
| **yield**  | 当前协程主动让出 CPU，切换到调度器或其他协程。yield也就是从协程中切换到mian函数中的过程。 | 说一句“我先歇会儿，让别人干” |

另外两个辅助原语：

* **exit**：协程执行完毕，自动销毁

* **schedule**：调度器，决定下一个运行哪个协程

### （4）调度器实现以及执行策略

io没有就绪，则切换yeild

io就绪了，则恢复resume

协程大小依赖于stack栈提供的大小



为了简化说明，我们采用 **FIFO（先入先出）** 的调度策略：

1. **创建**：协程创建后变为 `READY` 状态，放入调度器。
2. **调度**：调度器从就绪队列中取出一个协程，通过 `swapcontext` 切换过去。
3. **让出**：协程执行过程中，如果需要等待 IO 或主动让出 CPU，调用 `yield` 保存当前状态，切换回调度器主上下文。
4. **结束**：协程函数执行完毕，将状态置为 `DEAD`，切换回调度器。
   
   
   
   

### （5）执行流程

1. **Main 函数**初始化调度器。
2. **Main**创建协程 A，分配栈，初始化 `ucontext_t`，状态设为 `READY`。
3. **Main**调用 `resume` 协程 A：
   * 保存 Main 的上下文到 `scheduler->main_ctx`。
   * 恢复协程 A 的上下文 `coroutine->ctx`。
4. **协程 A**开始运行代码。
5. **协程 A**执行到一半，调用 `yield`：
   * 保存协程 A 的上下文到 `coroutine->ctx`。
   * 状态设为 `SUSPEND`。
   * 恢复 `scheduler->main_ctx`，返回到调度器。
6. **调度器**查找下一个就绪协程（例如协程 B），重复步骤 3。
   
   
   
   
   
   

### （6）协程的多核模式

协程是封装在应用层的，他需要依赖于底层的多线程或者多进程，在多线程时，调度器是共享的，因此需要对线程进行上锁。而多进程不共用调度器因此没有上锁问题，多进程实现更简单。性能上，多进程会更强。

## 2 reactor + coroutine

### 最佳方案

保留现有的 `epoll_wait` 主循环作为**驱动器**，当事件就绪时，唤醒对应的协程来执行业务逻辑（http_requset/http_response）。



### 在reactor上实现协程的原因？

职责分离：epoll擅长处理大量的连接，而协程擅长处理业务逻辑。即读到了数据之后怎么解析、怎么计算、怎么查数据库。

性能开销：如果有100w个连接，但是只有1k个活跃，那么为每个连接创建协程在epoll中等待，需要创建100w个stack，内存巨大浪费。而Reactor只要维护一个fd数组即可。

### 如何用到协程？

协程不负责accept和等待read数据，而是负责recv_cb已经成功把数据读取到rbuffer之后。流程改造如下：

1. **Reactor 层**：`epoll_wait` 发现 `fd` 可读 -> 触发 `recv_cb` -> `read` 数据到 `rbuffer`。
2. **调度层（新增）**：`recv_cb` 通知调度器：“fd X 的数据到了，请处理”。
3. **协程层**：调度器恢复 fd X 对应的协程。
4. **业务层（协程内）**：

```c
    // 此时看起来像同步代码，实际上数据已经在内存里了
    http_requset(conn); 
    // 模拟业务处理耗时，让出CPU
    coroutine_yield(); 
    http_response(conn);
    // 处理完毕，协程结束/挂起，等待下一次 epoll 事件
```



实现流程：

```c
主线程epoll_wait检测到可读事件
recv_cb读取数据
创建协程，加入就绪队列
execute_ready_coroutines()来执行协程
协程执行http_request 和response
协程完成后标记为DEAD
返回主循环继续epoll_wait
```

```c
// 协程结构体
struct coroutine {
    int id;
    enum CoroutineState state;  // READY/RUNNING/SUSPEND/DEAD
    ucontext_t ctx;             // 上下文（保存寄存器、栈指针等）
    char *stack;                // 独立的栈空间（128KB）
    struct scheduler *sch;      // 所属调度器
    void (*func)(void *arg);    // 协程入口函数
    void *arg;                  // 函数参数
    struct coroutine *next;     // 就绪队列指针
};

// 调度器结构体
struct scheduler {
    ucontext_t main_ctx;        // 主协程上下文（Reactor线程）
    struct coroutine *running;  // 当前运行的协程
    struct coroutine *ready_queue_head; // 就绪队列头
    struct coroutine *ready_queue_tail; // 就绪队列尾
};


// 创建协程
struct coroutine* coroutine_create(struct scheduler *sch, 
                                   void (*func)(void *), void *arg) {
    struct coroutine *co = malloc(sizeof(struct coroutine));
    co->func = func;    // 保存协程要执行的函数指针
    co->arg = arg;    // 保存函数的参数
    co->state = COROUTINE_READY;    // 初始状态为"就绪"
    co->stack = malloc(COROUTINE_STACK_SIZE);  // 128KB独立栈

    getcontext(&co->ctx);    // 获取当前的上下文
    co->ctx.uc_stack.ss_sp = co->stack;         // 设置栈
    co->ctx.uc_stack.ss_size = COROUTINE_STACK_SIZE;
    co->ctx.uc_link = &sch->main_ctx;           // 协程结束返回主上下文

    // 设置入口函数：切换到ctx时，会执行 coroutine_entry 函数
    makecontext(&co->ctx, (void (*)(void))coroutine_entry, 1, co);
    return co;
}

// 协程切换：保存当前上下文，恢复目标上下文
void coroutine_resume(struct coroutine *co) {
    struct scheduler *sch = co->sch;
    struct coroutine *curr = sch->running;  // 当前运行的协程

    sch->running = co;
    co->state = COROUTINE_RUNNING;

    if (curr) {
        // 从当前协程切换到目标协程
        swapcontext(&curr->ctx, &co->ctx);
    } else {
        // 从主线程切换到目标协程
        swapcontext(&sch->main_ctx, &co->ctx);
    }

    sch->running = curr;  // 恢复
} 


让出CPU
void coroutine_yield() {
    struct scheduler *sch = g_sched;
    struct coroutine *curr = sch->running;

    curr->state = COROUTINE_SUSPEND;
    // 切换回主协程（Reactor线程）
    swapcontext(&curr->ctx, &sch->main_ctx);
}


```





在这个混合架构（Reactor + Coroutine）中，确实体现了生产者-消费者的设计模式，但这里的“商品”和“市场”比较特殊：

* **生产者**：**内核** + **Reactor 主循环**。
  * “商品”是 **“I/O 事件”（可读、可写）**。
  * 当网卡收到数据包，内核将其放入 socket 接收缓冲区，并通过 `epoll_wait` 通知 Reactor。Reactor 随后“生产”了一个就绪事件，唤醒对应的协程。
* **消费者**：**协程**。
  * 协程从挂起状态被唤醒（消费事件），读取并处理数据。
* **市场/缓冲区**：**`epoll` 实例 + 就绪队列**。
  * `epoll` 维护着所有连接的状态，只有就绪的连接才会被送到“市场”上供协程消费。

这种模式解耦了“等待 I/O”和“处理 I/O”，使得 Reactor 可以快速分发事件，而协程可以专注于复杂的业务逻辑处理。



关于协程依赖的框架：单线程多协程 (M:N 模型的特例)

你问到“协程是依赖于多线程或者多进程的框架来完成设计的”，在这个具体的解决方案中，我采用的是 **“单线程 Reactor + 多协程”** 的框架，也被称为 **M:N 模型中的 1:N 模式**（1 个 OS 线程对应 N 个协程）。

#### 具体解释

在这个方案中，整个网络程序**只使用一个主线程**（即 `main` 函数所在的线程），没有创建额外的 `pthread`。

* **底层载体**：这 1 个 OS 线程。
* **上层逻辑**：成千上万个协程（`struct coroutine`）。
* **调度方式**：所有协程都在这**一个** CPU 核心上通过 `ucontext`（或 swapcontext）进行**协作式多任务**切换。

#### 为什么选择单线程框架？

1. **极致性能（无锁化）**：
   
   * Reactor 处理百万级连接时，最大的开销往往是锁竞争。如果多个线程同时操作 `epoll` 和 `conn_list`，就需要加锁。
   * 使用**单线程**，所有资源（连接列表、epoll_fd、全局变量）都是线程私有的，**完全不需要加锁**。这是 C10M 级别服务器优化的核心技巧。

2. **天然协程安全**：
   
   * 因为只有一个 CPU 在跑，所以协程 A 在修改内存时，协程 B 绝对不会同时运行。这避免了复杂的多线程同步问题（死锁、竞态条件），大大降低了 `http_request` 等业务逻辑的编写难度。

3. **上下文切换成本低**：
   
   * 线程切换需要陷入内核，开销大（微秒级）。
   * 单线程内的协程切换只是用户态的寄存器拷贝，开销极小（纳秒级）。

#### 这种框架的局限性（以及如何解决）

当然，单线程框架也有弱点：**无法利用多核 CPU 的计算能力**。如果 `http_request` 里的业务逻辑非常耗 CPU（比如加密解密、大数据压缩），单线程就会卡住，导致其他连接的响应变慢。

**解决多核利用的方法（演进）：**

如果你需要利用多核，不要在 Reactor 内部加锁，而是采用 **“多进程”** 或 **“多 Reactor 线程”** 模型：

* **多进程模式（推荐，如 Nginx）**：
  
  * 主进程启动时，根据 CPU 核心数（比如 8 核），`fork` 出 8 个子进程。
  * 每个子进程都**独立运行**一份完整的“单线程 Reactor + 协程”代码。
  * 操作系统会自动将流量负载均衡到这 8 个进程上。
  * 这样既利用了多核，又保持了每个进程内部的无锁特性。

* **多 Reactor 线程模式（如 Netty）**：
  
  * 主线程只负责 `accept`。
  * 创建一组 Worker 线程，每个 Worker 线程有自己的 `epoll` 和协程调度器。
  * 连接建立后，通过某种算法（如取模）绑定到某个固定的 Worker 线程上，之后该连接的所有读写都在这个线程内完成。
